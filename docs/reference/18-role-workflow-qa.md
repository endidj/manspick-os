# 역할별 전체 워크플로우 QA 조사·체험 체크리스트

조사일: 2026-11-06. 대상: 현재 저장소의 landing/user/admin 앱, API Worker, domain/contracts/web, D1 마이그레이션과 테스트.

이 문서는 **현재 코드에서 확인한 기능과 제품 요구사항을 기준으로 만든 250개 QA 시나리오**다. 같은 시나리오의 상품·기기·역할·경계값 조합은 별도 실행 건으로 확장한다. 모든 가능한 입력 조합을 열거했다는 의미는 아니다. 이번 작업은 코드 조사와 기존 자동 회귀 검사이며, 아래 수동 시나리오를 실제 브라우저에서 모두 실행했다는 뜻이 아니다.

현재 구현 판정은 코드가 우선이며, 과거 구현 현황 표보다 [최신 대응 기록](13-figma-parity.md)을 우선 참고했다. Figma 원본·외부 서비스·운영 환경은 이번 조사에서 직접 검증하지 않았다. 기존 [PRD](../01-product-requirements.md)의 19개 요구사항·86개 수용 기준도 확인했지만, 아래 표는 AC별 검증 완료 선언이 아니다. 실행 결과는 아래 기록 기준에 따라 시나리오 ID로 남긴다.

시나리오는 수동 검증에 사용한다. 표의 구현 판정과 코드상 한계는 조사일 기준이므로 실행 전에 관련 코드와 테스트를 확인한다.

## 1. 역할과 체험 범위

| 역할       | 진입점                                      | 체험할 주요 업무                                                | 권한 경계                             |
| ---------- | ------------------------------------------- | --------------------------------------------------------------- | ------------------------------------- |
| 방문자     | `http://localhost:3000`                     | 서비스·상품·추천·FAQ·예약 이동                                  | 공개 정보만                           |
| 고객       | `http://localhost:3001/start`, `/s/{token}` | 접수·입금 요청·설문·준비·셀렉·결과·수정·후기·원본               | 인증한 한 촬영만                      |
| CEO / 대표 | `http://localhost:3002`, 역할 `admin`       | 전체 운영 + 상품·가격·배정 기준·운영 설정·이벤트·이력           | 관리자 전용 변경 가능                 |
| 운영 직원  | 같은 앱, 역할 `staff`                       | 전체 촬영·수동 접수·입금 확인·재배정·요청·수동 안내             | 관리자 설정 변경 불가, 상품 조회 가능 |
| 디렉터     | 같은 앱, 역할 `director`                    | 배정 고객·설계·준비 공유·현장 체크·후보 공개·확정된 디렉터 셀렉 | 배정 촬영만, 결제·대표 설정 불가      |
| 보정가     | 같은 앱, 역할 `retoucher`                   | 배정 작업·선택 사진·보정 선호·수정 의견·결과 전달               | 개인정보·전체 설문·미배정 작업 비노출 |

CEO는 별도 `ceo` 역할이 아니라 `admin`에 해당한다. 현재 역할에 없는 지점장·외주 보정가·상담사·회계 담당 등의 별도 권한을 이미 구현된 기능으로 가정하지 않는다.

직원 메뉴는 `/?view=board`, `detail`, `calendar`, `retouch`, `templates`, `packages`, `followups`, `settings`를 사용한다. `list`, `requests`, `notifications`도 일부 직접 주소로 제공한다. 디렉터는 `my-customers`, `today`, `calendar`, `profile`, 보정가는 `retouch`, `completed`가 주 메뉴다. 상세는 `/shoots/{id}`이며 디렉터의 `?screen=manage`, `field`, `candidates`와 보정 전용 화면이 있다. **메뉴 숨김만으로 접근 차단을 판정하면 안 된다.** `board`/`list` 직접 주소는 역할 공통 호환 경로가 있으므로 서버가 반환하는 데이터 범위를 함께 검사한다.

## 2. 시작 방법·데이터 준비

- 기존 로컬 DB가 준비돼 있으면 `yarn dev`로 네 서비스를 실행한다. 앱 간 쿠키 확인을 위해 브라우저 주소는 `localhost`로 통일한다.
- **기존 DB에 `yarn db:init`을 다시 실행하거나 D1/R2를 초기화·삭제하지 않는다.** 최초 설치 방법과 데이터 상태는 [README](../../README.md)를 따른다.
- 고객용 브라우저 프로필과 직원용 프로필을 분리하면 인계 QA가 쉽다. 직원 4역할을 동시에 열려면 서로 다른 프로필/격리 컨텍스트를 사용한다. 같은 프로필의 직원 탭은 쿠키를 공유하므로 역할 변경이 다른 탭에 영향을 준다.
- 직원 데모 로그인은 역할마다 활성 직원 중 ID 순 첫 한 명을 선택한다. 기본 seed는 역할별 한 명뿐이다. 디렉터 A/B·보정가 A/B·비활성 직원의 거부 경로는 별도 격리 fixture가 필요하다. 기본 역할 선택만으로 다른 직원인 척했다고 해석하지 않는다.
- 샘플 조작은 실제 로컬 상태를 바꾼다. 아래 상태/뒤 4자리는 최초 seed 기준이며 반복 QA 시 현재 상태를 다시 기록한다. 특히 인증 실패 잠금·IP 제한은 다른 샘플 체험에도 영향을 줄 수 있다.

| 구간                | 개인 링크                                         | 뒤 4자리 |
| ------------------- | ------------------------------------------------- | -------- |
| 입금 확인 대기      | `http://localhost:3001/s/demo-payment-access`     | `1001`   |
| 설문·촬영 준비      | `http://localhost:3001/s/demo-preparation-access` | `1002`   |
| 셀렉                | `http://localhost:3001/s/demo-selection-access`   | `1003`   |
| 결과·수정·후기·원본 | `http://localhost:3001/s/demo-result-access`      | `1004`   |

| 데이터 축 | 필요한 종류                                                                                    |
| --------- | ---------------------------------------------------------------------------------------------- |

| 상품      | ONE/HYBRID/ALLDAY, 옵션 없음·헤어·대여·코디·쇼핑·복합, 판매 중단 상품·옵션, 추가 보정 중단     |
| 일정      | 정상·휴무·전부 마감·동시 경합, 쇼핑 전 슬롯, 올데이 4슬롯, 서울 자정·월말·연말                 |
| 입금      | 본결제·초과 셀렉·추가 보정, 대기·확정·만료·해제, 만료 직전/직후, 신고액과 실제액 불일치        |

새 fixture를 운영 데이터에 섞지 않는다. 이 조사에서는 DB·seed·실제 예약·원격 리소스를 변경하지 않았다.

## 3. 판정·우선순위

- **P0**: 개인정보 누출, 역할·촬영 범위 침범, 중복 예약·금액 오류, 입금/공개 게이트 우회, 데이터 부분 저장 등 핵심 무결성.
- **P1**: 주요 업무를 끝내지 못함, 잘못된 다음 행동·인계, 복구 불가, 필수 사용성 문제.
- **P2**: 보조 기능·표현·확장 규모·편의성. 실제 영향이 크면 승격한다.
- **구현**: 현재 코드에 실행 경로가 있다. QA 통과를 의미하지 않는다.
- **부분**: 경로는 있지만 제한·미연결·구현 불일치가 있다. 작동 부분과 부족 부분을 각각 기록한다.
- **미연결**: 향후 연동/구현 후 검증할 항목. 정상 체험에서 성공했다고 처리하지 않는다.
- **정책**: 기대 결과를 운영 결정으로 먼저 확정할 항목. 임의 기준으로 PASS를 만들지 않는다.

실행 후 시나리오 ID, `PASS / FAIL / BLOCKED / N/A`, 역할·환경·브라우저·화면 폭·테스트 촬영 ID·실제 결과·증거·이슈 번호·실행자·실행일을 남긴다. 자동 회귀 결과와 수동 체험 결과는 별도로 기록한다.

## 26. 실행 순서·기록·완료 기준

1. 샘플4개로 각 구간을 먼저 탐색하고, 새 테스트 고객으로 E2E01→04→06→08을 하나의 촬영에 연결한다.
2. 디렉터 셀렉·추가금·추가 보정·복합옵션·올데이·만료/취소·재배정 분기를 E2E02/03/05/07/09/10/11로 실행한다. 상호 배타 분기는 별도 촬영을 쓴다.
3. SEC/AUT의 허용·거부 경로와 P0 동시성/저장 실패 검사를 수행한다. 단순 역할 전환 외 A/B 직원 fixture를 사용한다.
4. 모바일/키보드/느린 통신·규모 검사를 반복한다. FUT는 미연결/정책 대기로 남기고 별도 출시 잔여 항목으로 관리한다.

각 실행에는 ID, 실행자/역할, shoot ID, 브라우저/화면폭, 선행상태, 기대결과, 실제결과, PASS/FAIL/BLOCKED/N/A, 스크린샷/요청응답/이력, 이슈번호를 남긴다. 증거에는 실제 전화번호·원문 토큰·세션·개인 사진을 불필요하게 포함하지 않는다.

P0 실패가 없고, 주요 역할별 정상 인계와 거부 경로가 통과하며, P1 업무 중단과 설명되지 않은 저장 실패가 없을 때 현재 로컬 범위를 인수할 수 있다. 미연결 항목을 PASS로 바꾸거나 단위 검사 통과를 운영 출시 승인으로 바꾸지 않는다. 기대 정책이 없는 항목은 BLOCKED/정책결정 필요로 구분한다.
