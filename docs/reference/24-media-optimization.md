# 랜딩 사진·폰트 최적화

사용자가 승인한 적용 범위는 랜딩의 정적 사진과 폰트 로딩이다. 원본 디자인·애니메이션·서체·검색 제외 정책을 유지한다. 고객 업로드 사진, R2, DB, API 권한은 변경하지 않는다.

## 이미지 생성과 배포

원본 72개(74,144,842B)를 보존하고 웹에서는 WebP 182개(19,462,480B, 모든 크기의 합계)만 사용한다. 첫 화면 전송량은 이 전체 용량과 다르며 브라우저가 `sizes`와 화면 밀도에 따라 필요한 크기를 선택한다. 파생본은 EXIF 방향을 픽셀에 반영한 뒤 sRGB로 변환하며 EXIF/GPS·XMP·IPTC·ICC·주석을 제거한다. 원본 해시와 생성 결과의 해시·메타데이터를 검사한다. OG JPEG는 기존 1200×630px 파일이며 메타데이터가 없는 것을 별도로 확인했다.

```sh
yarn images:generate
yarn images:check
```

사진 교체 때 첫 명령을 실행하고 원본 manifest·생성 파일·생성 모듈을 함께 커밋한다. 소스 해시·설정·도구 버전이 동일하고 출력이 온전하면 재사용한다. 일반 앱 빌드에는 인코딩을 연결하지 않는다. `--check`는 파일을 쓰지 않고 결과가 오래되거나 손상됐으면 실패한다. 검증된 생성 디렉터리 밖의 파일은 정리하지 않는다.

최초 전체 변환은 당시 PC의 자원 경합 상황에서 574.4초가 걸렸다. 같은 환경의 재실행은 4.146초, 인코딩 0개·재사용 182개였다. 최초 수치를 CI나 다른 PC의 예상 시간으로 사용하지 않는다. 이후 작업은 원본 하나·Sharp 스레드 하나·32MB 캐시로 제한했다.

## 화면 연결

- 디자인 시스템의 공개 `sourceImages`에 크기별 URL·픽셀 치수를 제공한다. 기존 `sourceImageUrls`도 웹용 기본 URL로 호환한다.
- 랜딩 전용 `SourceImage`는 기존 이미지에 `srcset`·`sizes`·치수를 붙이며 별도 DOM 래퍼나 스타일을 추가하지 않는다. 기존 `PhotoTile`은 선택 테두리와 레이아웃을 포함하므로 원본 마크업 보존에 맞지 않아 사용하지 않았다.
- 36–40px 아바타에는 96/192px 사본을 제공한다. 그 외 사진은 원본 이내의 480/960/1600px 규격을 사용한다.
- 갤러리는 열릴 때 이미지를 생성하고 슬라이드는 화면에 가까워졌을 때 다음 이미지 하나를 준비한다. 디코딩한 후 기존 전환 시간에 교체하며 언마운트 때 정리한다.
- 해시가 포함된 `/_next/static/*` 자산은 1년 immutable 캐시를 지정한다. 기존 검색 제외 헤더를 유지한다.

## 폰트

기존 WOFF2·Pretendard 92개 unicode-range 조각·Geist·라이선스·`font-display: swap`을 유지한다. 모든 화면은 공통 Pretendard 조각91만 먼저 요청하며, 숫자/영문 서체를 사용하는 메인·추천 화면에만 Geist 힌트를 둔다. 약관·개인정보 화면에는 Geist preload가 없다.

동일 배포 HTML의 80ms·2Mbps 단일 비교에서는 390/1440px 모두 제목·hero 배치가 같았고 폰트 18개·517,012B, 중복 요청 0건이었다. 주요 폰트 요청 시작은 약0.7–0.9초 빨랐다. 이 관찰은 폰트 바이트 절감이나 LCP 개선을 의미하지 않는다.

## 검사

생성 단위 검사는 방향·투명도·메타데이터 제거·캐시 재사용·손상 복구·오래된 결과 탐지를 다룬다. 브라우저 검사는 반응형 사진 선택·초기 전송 예산·갤러리 지연 로딩·슬라이드 교체·폰트 힌트/중복 요청과 기존 화면·추천 흐름을 확인한다. 실제 고객 정보를 전송하지 않는다.
