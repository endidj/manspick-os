# 여러 제품과 고객사에 재사용할 뼈대

맨즈픽을 첫 번째 운영 사례로 삼고, 두 번째 회사는 **같은 코드에서 별도 배포**하는 것을 권장한다. 각 회사가 도메인, 직원 목록, Worker, D1, 비공개 R2, 발송 계정과 백업을 별도로 갖는다. 회사마다 저장소를 복사해 고치면 버그 수정이 갈라지므로, 공통 저장소에서 버전을 내고 회사별 설정과 업무 모듈을 조합한다. 운영 화면·고객 화면·공개 사이트는 필요한 경우에만 설치한다.

## 공통화 우선순위

| 순서                  | 공통으로 가져갈 것                                                                               | 제품별로 정할 것                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 1. 직원 계정·로그인   | 계정 등록·초대·역할 변경·비활성화, 로그인·로그아웃·세션 만료와 회수, 로그인 화면 상태, 인증 가드 | 이메일 링크 또는 SSO, 허용 도메인, 기본 역할, 고객 로그인 방식                  |
| 2. 권한과 데이터 범위 | 검증된 사용자로 서버에서 행위 권한과 조회 범위를 함께 검사하는 방식, 화면에 전달할 허용 동작     | 역할별 허용 동작, 본인·담당·지점 범위, 응답에서 가릴 개인정보, 업무 상태별 조건 |
| 3. 관리자 화면 틀     | 데스크톱·모바일 탐색, 목록·검색·필터·페이지 이동, 상세·편집, 로딩·빈 상태·저장 실패 표현         | 메뉴, 화면 경로와 데이터, 업무 동작, 브랜드·문구                                |
| 4. 감사 기록과 파일   | 행위자·행위·대상·시각·결과를 남기는 형식, 비공개 파일 검사·업로드 재시도·권한 확인 후 다운로드   | 남길 변경과 가릴 필드, 파일 유형·공개 조건·보존 기간                            |
| 5. 설치·인수인계      | 환경 설정과 검증, 초기 관리자·마이그레이션, 가상 시드, 상태 확인·로그, 내보내기·백업·복구 절차   | 도메인·시간대·리소스, 켤 앱과 업무 모듈, 이메일·알림·결제 공급자와 비밀값       |

### 현재 코드에서 시작할 곳

- **인증.** 직원의 일회용 이메일 링크와 고객의 촬영 링크 인증을 나누고, 두 방식에서 세션 쿠키와 발급·만료·폐기를 공유한다. 관리자 앱에서는 직원 세션과 제품 메뉴 이동을 분리한다. 대표는 직원을 등록하고 역할·활성 상태를 바꾸거나 로그인 자격을 회수할 수 있다. 세션과 미사용 링크는 권한을 변경한 트랜잭션에서 함께 폐기한다. [직원 로그인](../../apps/server/src/security/staff-login.ts) · [서버 세션](../../apps/server/src/security/sessions.ts) · [관리자 직원 세션](../../apps/admin/src/features/authentication/use-staff-session.ts)
- **인가.** Nest의 `AccessGuard`가 요청과 행위자를 확인하고, 공개 경로와 역할 제한은 `@Public()`·`@RequireRole()`로 선언한다. 요청 문맥은 `AsyncLocalStorage`로 분리한다. 촬영·파일 업무는 배정과 공개 조건까지 검사한다. 예를 들어 디렉터는 배정된 촬영만 조회할 수 있다. 같은 범위 정책을 목록·상세·파일에 적용하고, 화면의 버튼 표시는 서버가 허용한 동작을 반영한다. 사용자별 역할 배정에서 시작하고 개별 권한 예외는 실제 필요가 생기면 사유·만료와 함께 기록한다. 구체 역할명과 `finish_retouch` 같은 촬영 명령은 맨즈픽 모듈에 둔다. [접근 가드](../../apps/server/src/http/access.ts) · [촬영 조회](../../apps/server/src/shoots/access.ts) · [파일 접근](../../apps/server/src/files/access.ts)
- **화면과 요청.** 디자인 시스템의 입력·탭·대화상자·상태 컴포넌트와 웹 클라이언트·프록시를 재사용한다. 관리자 셸에는 제품별 메뉴·브랜드를 연결한다. API 계약은 `contracts`, 업종별 순수 규칙은 해당 제품의 `domain`, 인가·저장은 서버가 맡는다. [디자인 시스템](../../packages/design-system/README.md) · [웹](../../packages/web/README.md) · [관리자 셸](../../apps/admin/src/features/shell/admin-shell.tsx) · [계약](../../packages/contracts/README.md) · [도메인](../../packages/domain/README.md)
- **로그.** 직원·설정·템플릿 변경은 같은 감사 이벤트 형식으로 실제 변경과 함께 저장한다. 운영 오류는 요청 ID와 오류 코드로 추적한다. 촬영의 고객·직원용 진행 타임라인은 업무 화면의 읽기 모델로 유지한다. [감사 이벤트](../../apps/server/src/activity/audit.ts) · [운영 로그](../../apps/server/src/runtime/log.ts)

### 두 번째 납품에서 검증할 것

1. 회사별 설치 명세로 같은 커밋을 A와 B에 설치한다. 브랜드, 시간대, 앱·메뉴·업무 모듈, 도메인, 저장소·발송 바인딩, 최초 관리자와 기본 역할을 설정한다. 비밀값은 런타임에 넣는다.
2. 두 번째 제품에서 **직원 로그인 → 권한으로 제한된 목록과 상세 → 변경과 감사 기록** 한 흐름을 완성한다. 양쪽에서 쓰는 세션·인가·셸만 기존 앱과 패키지 경계 안에서 분리한다. 공급자 교체, 파일·알림·결제는 해당 납품에서 필요할 때 연결한다.
3. A의 계정·세션·링크·파일을 B에서 사용할 수 없는지 검증한다. 역할 변경·비활성화·재활성화, 다른 담당자의 상세·다운로드 차단도 검사한다. 빈 DB 설치와 기존 데이터 마이그레이션을 각각 확인하고 같은 공통 업데이트를 적용한 뒤 두 제품의 대표 업무를 다시 실행한다.

## 데이터 설계

현재 D1을 운영 원장으로 유지한다. 예약, 고객, 배정, 결제, 파일, 보정 요청은 서로 연결되고 한 번의 작업에서 여러 기록의 일관성이 필요하다. 변경 가능한 상품과 예약 당시의 상품 스냅샷은 분리한다. 설문 답변처럼 구조가 바뀌는 입력은 원본 JSON과 설문 버전을 남기고, 실제 검색·정산에 쓰는 값은 컬럼이나 관계 테이블로 승격한다. 사진 파일은 R2, 사진 관계·권한·객체 키는 D1에 둔다.

온톨로지를 하려면 먼저 업무 용어와 관계를 정의한다. 예를 들어 `고객 → 촬영 → 후보 컷 → 보정본 → 수정본`, `예약 → 당시 상품 → 담당자 → 입금 확인`이다. ID를 안정적으로 보관하고 생성·변경 시각, 행위자, 출처, 이벤트 버전을 기록한다. 현재 타임라인은 사람이 읽는 운영 기록이다. 분석에 실제로 쓰이는 `booking_created`, `deposit_confirmed`, `results_delivered` 등은 해당 업무 변경과 같은 저장 단위에서 구조화 이벤트로 남기고, 회사별로 익명화한 분석 뷰나 CSV로 내보낼 수 있게 한다. 예를 들어 접수부터 결과 전달까지 걸린 시간, 상품별 추가 보정 전환, 작업자별 재수정 비율을 계산할 수 있다.

원장은 D1으로 시작하고, 복잡한 임의 시간대 예약·동시 쓰기·대형 집계 요구를 실제로 측정한 뒤 PostgreSQL을 검토한다. 그래프 DB는 여러 관계를 반복해서 탐색해야 하는 질의가 실제로 생겼을 때 운영 원장에서 만든 읽기용 모델로 검토한다. 통합 SaaS는 고객 가입, 공통 과금과 운영, 고객 간 격리 검증을 별도 제품으로 감당할 규모가 되었을 때 결정한다.

## 현재 맨즈픽 운영 인수인계

- 공통 API는 NestJS·Express를 Workers의 Node HTTP 호환 계층에서 실행한다. 독립 Node.js 프로세스가 아니며 Nest의 공식 지원 런타임도 아니므로 Node 회귀 검사와 실제 Cloudflare 실행을 함께 확인한다. shutdown hook·WebSocket gateway·TCP microservice에 의존하는 기능을 추가하기 전에는 배포 런타임을 다시 검토한다. [서버 구조](../../apps/server/README.md) · [NestJS 전환 기록](21-nestjs-migration.md)
- 현재 저장소에 준비된 API 원격 설정은 비공개 `manspick-api-test`이다. 관리자 테스트 앱의 Service Binding과 전용 D1·R2를 사용하며, 테스트 배포를 회사 운영 배포로 간주하지 않는다. 배포 후 상태 확인, 로그인·권한 거부, 파일 응답을 실제 Cloudflare 경로에서 검증한다.
- 운영 API Worker는 `LOCAL_DEMO`와 `ADMIN_TEST`를 켜지 않는다. 데모 시드는 테스트에서만 사용한다. 직원은 검증한 회사 도메인의 실제 주소로 등록하고 활성 상태와 역할을 확인한다.
- [운영 API 설정 예시](../../infra/wrangler.production.example.jsonc)를 복사해 실제 회사 리소스 이름·ID와 도메인을 넣는다. 각 화면 앱의 `MANSPICK_API` Service Binding은 그 회사의 API Worker만 바라보게 맞춘다. 랜딩 빌드에 `NEXT_PUBLIC_CUSTOMER_APP_ORIGIN`과 `NEXT_PUBLIC_ADMIN_APP_ORIGIN`을 넣고, 고객 앱 빌드에 `NEXT_PUBLIC_LANDING_APP_ORIGIN`을 넣어 개인정보 안내 주소를 맞춘다. 예시 파일은 실제 운영 설정이 아니다.
- API Worker에 `STAFF_APP_ORIGIN`, `CUSTOMER_APP_ORIGIN`을 HTTPS 도메인으로 설정한다. `STAFF_EMAIL_DOMAIN`은 허용할 회사 도메인 하나, `STAFF_EMAIL_FROM`은 승인된 발신 주소다. [Cloudflare Email Sending Workers API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/)에서 `send_email` 바인딩 이름을 `EMAIL`로 지정한다. 직원 인증과 파일 재시도 마이그레이션을 적용한 스테이징에서 실제 메일 도착, 로그인, 계정 비활성화 후 세션 차단을 확인한다.
- 새 예약은 운영자가 고객 상세의 **고객 접속 링크**에서 발급하고, 같은 화면의 등록 연락처로 확인한 고객에게 별도로 전달한다. 링크와 연락처를 확인한 행위는 이력에 남고, 재발급 즉시 이전 링크와 기존 고객 세션은 무효다. URL과 전화번호 원문을 티켓·메모·로그에 남기지 않는다. 자동 알림톡과 실결제 연동은 공급자와 운영 승인이 필요하다.
- 진행 중이던 보정 작업의 과거 파일에 요청 컷 연결이 없으면 새 완료 검사를 통과하지 못한다. 운영자가 작업을 확인해 올바른 컷을 선택하고 결과를 다시 올린다. 이미 전달 완료한 과거 작업은 그대로 유지한다.
- D1 시점 복구와 R2 객체 복구를 함께 연습한다. DB만 복구해도 이미 삭제된 파일은 돌아오지 않는다. 장애 로그는 요청 ID, 회사·기능, 결과 코드, 소요 시간을 중심으로 남기고 고객 연락처, 원본 파일 주소, 인증 토큰은 제외한다. 내보내기·복원·권한 회수 책임자를 정한 뒤 운영으로 전환한다. [D1 백업·시점 복구](https://developers.cloudflare.com/d1/reference/time-travel/)와 [D1 운영 한도](https://developers.cloudflare.com/d1/platform/limits/)는 요금제 및 환경별로 확인한다.

납품 범위도 별도로 쓴다. 1차 검수는 맨즈픽의 실제 운영 흐름과 인수인계, 2차 검수는 두 번째 회사에서 동일한 공통 기능의 재사용과 데이터 격리 시연으로 나눈다. 신규 회사마다 추가로 만드는 업무·데이터 이전·외부 연동·운영 지원과, 재사용 가능한 공통 코드 및 고객사 전용 자산의 범위를 제안서에 명시한다.
