# 고객·관리자 Figma 일치 작업

## 기준과 범위

- 2026-11-06 브라우저의 Figma 원본에서 고객 23화면·설계 메모 23개와 내부 14화면을 PNG 1배율로 내려받았다. 비교 원본은 `.local/figma-parity/`에 보관한다.
- 고객 390px, 관리자 보드 1920px, 상세·설정·스케줄 1440px, 디렉터 390px를 각각 비교한다. 화면을 합쳐 놓은 기존 구현을 원본의 개별 상태와 작업 화면으로 나눈다.
- 실제 고객·수치·사진은 API 데이터를 사용한다. 원본의 예시 계좌·주소·고객명을 운영 데이터로 복사하지 않는다.
- 확정 가격(원 95,000원·하이브리드 160,000원·올데이 500,000원), 수정 최대 3회, 후기 승인 후 원본 공개 정책을 유지한다.

## 변경 전 확인

- 기존 사용자 앱은 홈·설문·준비·사진·후기의 다섯 탭으로 원본 23화면을 합쳤다. 준비/촬영 설계/당일과 셀렉/전달/수정 요청이 구분되지 않는다.
- 기존 관리자 앱은 보드·목록·일정표·요청·알림·읽기 전용 설정을 제공한다. 원본 배정 matrix와 디렉터·보정가 전용 화면이 빠져 있다.
- 준비 가이드 읽음/전체 확인, 현장 체크, 셀렉 주체 확정, 수동 배정, 알림 수동 완료, 운영 설정 편집은 서버 계약도 함께 추가해야 한다.
- 기존 backend 회귀 19/20: 설문 독립 진행 테스트가 오늘 11:00 UTC 고정 마감 후 재제출을 기대해 시간에 따라 실패한다. 테스트의 마감만 미래로 고정하고 실제 편집 마감 규칙은 보존한다.

1. 상태별 고객 여정과 역할별 관리자 view를 순수 모델로 분리하고 회귀 테스트로 먼저 잠근다.
2. 두 앱은 기존 design-system의 공개 컴포넌트·토큰·아이콘과 packages의 공개 계약을 먼저 사용한다. 임의 탐색 탭을 원본 탐색 흐름으로 교체한다.
3. 기존 인증·담당자 범위·사진 접근·수정 제한을 유지하면서 빠진 저장 동작을 Hono 기능별 명령/라우트로 추가한다. 추가 D1 migration은 데이터 삭제 없는 테이블 추가만 수행한다.

## 패키지와 저장 경계

- 두 앱의 CSS에서 색상 HEX/RGB와 숫자 font-size/font-weight 사용을 제거했다. 공통 컴포넌트·의미 색상·타이포그래피 토큰을 우선하고 앱은 화면 배치를 소유한다. 기존 DS의 흩어진 색상도 토큰으로 연결했다.
- 사용자 결정에 따라 blue500 `#2D76F6`와 흰 글자를 유지한다. 대비 4.17:1의 알려진 조합만 Storybook 색상 대비 검사에서 제한적으로 제외한다. 나머지 접근성 검사는 유지하며 해당 버튼/선택 셀의 실제 계산 색상을 별도로 검사한다. AA 색상 대비 충족으로 보고하지 않는다.
- 독립 Hono Worker는 `apps/server`, 공유 DTO와 명령은 `@manspick/contracts`가 소유한다. 화면 앱은 Worker 실행부나 DB를 가져오지 않는다. 병행한 서버 구조 변경을 보존했다.
- 추가 D1 마이그레이션 0002~0004를 로컬에 적용했다. 기존 데이터나 R2를 초기화하지 않았다. 신규 옵션/상품 활성은 기존 컬럼을 사용한다.
- 수동 안내는 단계·상품·옵션·직원 조건의 AND/각 값 OR를 서버에서 적용하고 담당 촬영만 조회한다. 완료는 고유 제약으로 중복 기록을 막고 외부 발송을 수행하지 않는다.
- 보정가는 자기 작업 라운드와 수정 요청의 참조 사진만 열람한다. 미결제 추가 사진과 다른 보정가 작업을 차단하는 회귀를 추가했다.
- 현장에서 디렉터 셀렉으로 확정한 촬영은 관리자 후보/사진 화면에서 공개 후보를 의상별로 선택하고 실제 `submit_selection`으로 제출한다. 성공 후 잠그며 초과분은 기존 입금 확인 흐름을 따른다. 이 최종 선택 영역은 별도 원본이 없어 기존 고객 선택 패턴을 재사용했다.
- 수동 접수 창은 취소·성공 후 다시 열면 이전 고객의 정보·선택·성공 결과를 초기화한다. 모킹한 브라우저 회귀로 두 재진입을 확인했다.
- 운영 카드의 날짜는 공유 `dateTime(value, 'compact')`를 사용해 원본처럼 서울 시간의 `11/6 (금) 09:30`으로 표시한다. 기존 긴 날짜 형식은 유지한다.
- 보드의 부가서비스 필터는 촬영 당시 옵션 snapshot을 사용하고 기존 검색·기간·담당자·상품 조건과 함께 적용한다. 이전에 저장한 필터에 새 항목이 없어도 전체로 복원한다. 같은 조회 SQL에서 옵션을 모으므로 카드별 추가 조회는 없다.
- 상세 명령 성공 시 POST가 반환한 최신 상세를 즉시 반영한다. 성공 뒤 불필요한 GET의 실패를 저장 실패로 오인하지 않으며, POST 실패 때는 기존 상세와 재시도 경로를 유지한다.
- 상품 규칙은 원본의 스팟·하/중/상·옵션별 가중·별칭을 저장한다. 대여+코디 합계는 의상 수 이내, 쇼핑은 원/하이브리드 1회·올데이 2회, 올데이 헤어 별도 신청 제외를 기본으로 한다. 고객 수량 UI와 서버가 같은 규칙을 사용하며 선택한 모든 자격 필요 옵션을 일정 조회와 실제 배정에서 검사한다. 옵션 가중 합계는 신규 예약에 기록하지만 숫자 순위로 환산하지 않는다.
- 운영 기준 편집은 입금 유지/촬영 전 마감 시간, 예약 주 수, 기존 네 시간의 노출, 설문/의상 제출 일수를 실제 신규 예약에 적용한다. 기존 예약의 기한과 점유 슬롯은 보존한다. 설정은 관리자만 저장하며 JSON 설정과 상품 규칙은 같은 값을 읽은 요청끼리 경합할 때 덮어쓰지 않도록 검사한다.
- 추가 보정은 관리자 상품 목록의 사진 전용 항목을 단일 가격 출처로 사용한다. 신규 예약 옵션으로 구매하지 않으며 셀렉/추가 신청의 실제 주문에 단가를 저장한다. 판매 중단 시 기본 포함 컷은 유지하고 신규 초과/추가 주문만 막는다. 이미 접수한 주문 금액과 입금 확인은 유지한다.
- 관리자 수동 접수도 고객 예약과 같은 패키지별 수량·포함 옵션·디렉터 자격을 사용한다. 패키지를 바꾸면 신청 불가능한 옵션을 제거하고 수량을 조정한다. 서버 오류가 발생해도 고객 정보와 수량을 보존하며 재시도한다.

## 확인 범위와 남은 차이

원본 PNG 전체를 읽고 대응 화면을 구현한 것과 모든 원본 상태의 픽셀 단위 일치는 구분한다. 브라우저 대표 비교는 고객 홈/준비/셀렉/결과와 관리자 보드/상세/템플릿·모달/서랍을 중심으로 진행한다. 원본 예시 고객·사진·수치를 복제하지 않으므로 실데이터 길이와 장수에 따른 배치는 달라질 수 있다.

아래는 여전히 원본과 차이가 있거나 운영 결정을 기다리는 항목이다.

- I-6의 하/중/상 숫자 환산·디렉터별 수용치·동률 순위는 원본만으로 확정할 수 없다. 자격·휴무·슬롯 충돌과 기존 예약 수 순서를 사용하며 가중 합계를 임의 배정 점수로 만들지 않는다.
- I-12는 기존 11/13/15/17시의 노출을 조정하며 임의 시각으로 이동하지 않는다. 숨긴 시간도 올데이·쇼핑 점유에는 포함한다. 수정 최대 3회는 기존 DB 규칙으로 유지한다. 정책 카드 전체를 끄는 의미·보상 지급 조건·사진 보관 기간은 미정이며 가짜 저장/삭제 스위치를 만들지 않았다. 만료 정리·알림 리마인드의 자동 실행도 아직 연결하지 않았다.
- 기본정보만 제출한 시점의 중간 접수는 만들지 않으며 최종 일정 요청에서 예약을 생성한다. 외부 선결제는 실제 확인 수단 없이 자동 확정하지 않고 직원 확인을 기다린다. 선결제 자동 확정 정책은 기존 DEC-02 미결 사항이다.
- 원본 I-7에서 본문이 보인 준비물·의상 안내 외 템플릿은 운영자 검토 전 비활성 초안이다. 개인 링크는 저장된 해시에서 복원할 수 없어 `{OS링크}`를 임의 URL로 대체하지 않는다.
- 공식 카카오 URL·실제 운영 계좌/장소·정식 직원 인증·외부 결제/알림·전체 캠페인 지급·대량 ZIP·원격 배포는 연결하지 않았다.
