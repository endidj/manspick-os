# 계정·권한·개인정보 설계

## 개발 계약의 계정·권한 기준

- 고객은 주문 페이지에서 예약을 신청한 뒤 카카오 또는 구글로 가입·로그인하고 설문 페이지에 진입한다. 고객은 전용 페이지에서 본인의 정보와 설문 상태를 확인한다.
- 대표 화면에서 직원 정보와 역할을 관리한다. 직원 추가·삭제 권한은 현욱에게만 부여한다. 삭제는 계정 비활성화로 처리해 기존 기록을 보존한다.
- 운영직원은 고객 프로필과 예약을 조회해 문의에 응대한다. 디렉터는 자신에게 배정된 고객과 예약을 확인하고 촬영 일정을 확정한다. 담당 배정과 일정 확정 알림은 해당 고객을 맡은 직원의 개인 카카오톡으로 보낸다. 보정가도 담당 건 알림의 수신 대상이며, 계약상 어드민 화면은 대표·운영직원·디렉터 세 가지다.

계약의 전체 기능과 수용 기준은 [제품 요구사항](../01-product-requirements.md)을 따른다. 현재 서버의 인증·인가와 D1·비공개 R2 접근 경계는 [Cloudflare 아키텍처](../07-cloudflare-architecture.md)를 참고한다.

현재 직원 관리 API는 `admin` 역할을 검사한다. 계약 검수에서는 현욱 계정으로 직원 추가·삭제가 가능하고 다른 대표 계정으로는 두 작업이 모두 거부되는지 확인한다. [직원 계정 API](../../apps/server/src/security/staff-accounts.ts) · [관리자 세션 검사](../../apps/server/src/security/sessions.ts)

## 1. 초기 설계 기록의 기준 자료와 구분

이하 1~12절은 2026-11-06에 조사한 역할·권한·개인정보 설계와 당시 미결 사항을 보존한다. 개인 링크와 전화번호 뒤 4자리 인증, 보정가 전용 작업 화면, Supabase Auth·RLS·Storage는 이 초기 설계의 맥락에서 읽는다.

주요 근거는 [Canonical v1.11](https://app.notion.com/p/Canonical-Manspick-OS-398af8f3d6b0817d9a84da6b2e770aca), [Figma D3 API·권한 설계 v0.2](https://www.figma.com/design/cDXVLqZAaWwZeyIo5pqnNl/?node-id=172-2), [Notion API v0.2](https://app.notion.com/p/API-v0-2-3eeaf8f3d6b081b6aadcd72a0017fd0c)다.

아래의 **원문 정책**은 당시 자료에서 확인한 요구다. **설계 보완**은 그 요구를 서버·DB·파일에 일관되게 적용하기 위한 제안이다. 당시 상태·업무별 허용 조건은 [초기 PRD](../archive/01-product-requirements.md), DB 관계와 전이는 [초기 데이터·흐름](../archive/05-data-and-flows.md)에 기록했다.

고객과 직원은 인증 방식이 다르다. 고객은 회원 가입 없이 촬영 개인 링크로 접근한다. 직원만 Supabase Auth 계정과 staff 허용 목록을 사용한다. 기존 초안의 임의 역할인 시스템 책임자·운영 관리자·담당 직원 대신 원문 역할 값인 `admin`, `staff`, `director`, `retoucher`를 사용한다.

## 2. 인증 주체와 역할

| 주체      | 원문 정책                                  | 접근 범위                                               |
| --------- | ------------------------------------------ | ------------------------------------------------------- |
| 방문자    | 로그인 없음                                | 공개 안내와 `/start` 접수                               |
| 고객      | `/s/{token}` + 전화번호 뒤 4자리 확인      | 검증된 촬영 세션의 한 shoot와 고객에게 공개된 하위 자료 |
| admin     | Supabase 이메일 매직링크 + 활성 staff 등록 | 대표의 전체 운영, 설정·직원 권한·캠페인·가격 관리       |
| staff     | 같은 직원 인증, role=staff                 | 전체 촬영 운영. 관리자 설정·직원 권한·가격 관리 제외    |
| director  | 같은 직원 인증, role=director              | 본인에게 배정된 촬영과 하위 자료, 본인 휴무             |
| retoucher | 같은 직원 인증, role=retoucher             | 본인 retouch_jobs와 보정에 필요한 마스킹된 자료         |

직원 이메일은 `@manspick.co.kr`이며 staff.active 허용 목록을 함께 검사한다. 도메인만 맞는 사람이 자동으로 직원이 되는 구조가 아니다. 보정가는 내부 직원이다. 외주 보정가를 위한 제3자 계정·제3자 제공 동의 흐름을 추가하지 않는다.

인가 판단은 `인증 경로 + 활성 여부 + 역할 + 현재 배정 + 대상 촬영 + 동작 + 현재 업무 상태`를 함께 확인한다. 고객에게 촬영 전체의 모든 내부 정보가 공개되는 것은 아니며, director와 retoucher의 화면 표시 여부만으로 서버 권한이 생기지 않는다.

## 3. 고객 접수와 세션

### 원문 정책

1. 고객은 `/start`에서 옵션·기본정보·일정·결제·설문 흐름을 진행한다. 가입·이메일 인증·소셜 OAuth는 요구하지 않는다.
2. 같은 전화번호의 진행 중 촬영이 있으면 중복 생성하지 않는다. 응답에 고객 존재 여부나 개인 링크를 노출하지 않고 기존 링크를 **해당 전화번호의 알림톡으로만** 재발송한다.
3. 진행 중 촬영이 없는 재방문 고객은 같은 customers 행에 새 shoots를 만든다. 고객과 촬영은 1:N이다.
4. `/s/{token}` 진입 시 전화번호 뒤 4자리를 확인한다. 서버가 access_attempts를 기준으로 5회 실패 후 10분 잠금을 적용하고 IP별 시도 제한도 둔다.
5. 확인 성공 후 httpOnly 세션 쿠키를 사용한다. 브라우저 종료 시 끝나는 세션이며 장기 자동 로그인으로 바꾸지 않는다.
6. 토큰 재발급 시 이전 토큰은 사용할 수 없어야 한다.

전화번호 뒤 4자리만으로 기존 고객을 검색하거나 개인 링크를 반환하는 API를 만들지 않는다. 공개 접수의 번호 입력은 기존 촬영 정보의 열람 권한이 아니다. 개인 링크를 받은 고객도 뒤 4자리 확인을 통과하기 전에는 촬영 상세·이름·사진을 읽을 수 없다.

### 설계 보완

- 인증된 세션에는 서버가 확인한 shoot_id와 세션/토큰 버전만 권한 문맥으로 연결한다. 요청 body·query의 customer_id·shoot_id를 그대로 사용하지 않는다.
- 쿠키는 Secure·적절한 SameSite·host-only 범위로 제공하고 고객/직원 쿠키를 분리한다. 세션 쿠키에 장기 Expires/Max-Age를 설정하지 않는 기본안을 사용한다.
- 토큰 재발급은 이전 토큰에서 파생된 세션도 폐기하도록 버전 또는 서버 세션 검사를 추가한다. 토큰·세션 원문을 일반 로그에 남기지 않는다.
- 5회/10분 잠금은 인증 대상 기준으로 서버에서 판정하고, IP 제한은 이를 보완한다. IP 한도가 몇 회인지·공유망 예외는 운영 설정으로 확정한다. 브라우저 카운터만으로 제한하지 않는다.
- 만료·잘못된 토큰·확인 실패·기존 번호 접수의 응답은 정보 노출이 없는 공통 정책으로 정한다. 알림 재발송에도 별도 제한을 둬 타인의 번호로 반복 메시지를 보내지 못하게 한다.
- 쿠키를 사용하는 변경 요청은 Origin·CSRF 방어를 적용한다. 화면 리다이렉트와 버튼 비활성화 외에 각 서버 진입점에서 동일 검사를 실행한다.

## 4. 직원 인증과 계정 생애주기

### 원문 정책

Supabase Auth 이메일 매직링크로 인증하고, 도메인·등록된 staff·active·role을 확인한다. active=false인 직원은 업무에 접근할 수 없다. 역할 부여·변경과 공통 설정은 admin의 책임이다.

| 사건          | 처리                                                                        |
| ------------- | --------------------------------------------------------------------------- |
| 직원 등록     | admin이 staff 허용 목록과 역할을 관리. 인증된 Auth 사용자와 연결            |
| 로그인        | 이메일 매직링크 확인 후 staff 등록·도메인·active 검사                       |
| 역할 변경     | 다음 조회·변경·파일 발급부터 새 역할을 적용하고 이력 기록                   |
| 디렉터 재배정 | 이전 디렉터의 대상 촬영 접근 해제, 새 담당자 범위 적용, 변경 사유·이력 기록 |
| 퇴사·정지     | active=false, 이후 데이터·작업·파일 URL 발급 거부. 잔여 업무 인수인계       |
| 토큰 재발급   | 고객 촬영 링크의 이전 토큰 폐기. 직원 Auth와 별개로 관리                    |

### 설계 보완

- 이메일 도메인을 정확히 비교하고, 다른 도메인의 유사 주소나 사용자가 수정한 표시 이름을 허용 조건으로 사용하지 않는다.
- 사용자가 보낸 role·staff_id·Auth 메타데이터만으로 승격시키지 않는다. 현재 staff 행과 업무 배정을 신뢰 기준으로 삼는다.
- active·배정 변경은 오래된 JWT나 화면 캐시 때문에 계속 허용되지 않도록 RLS와 서버 검사에 반영한다. 기존 로그인 세션만으로 퇴사 후 접근이 유지돼서는 안 된다.
- 매직링크의 콜백·돌아갈 주소는 승인된 호스트/경로로 제한한다. 세션 교환·갱신은 공식 SSR 경계를 따르고 개인 응답을 공용 캐시에 공유하지 않는다.
- admin 자기 권한 변경·마지막 활성 admin 제거 방지, 민감 관리 작업의 재인증·MFA는 구현 전 운영 정책으로 확정할 보완 항목이다. 원문에 없는 필수 도구 가입을 추가하지 않는다.

직원 SSR 세션 구성은 [Supabase SSR](https://supabase.com/docs/guides/auth/server-side), 서버 인가 경계는 [Next.js 인증 가이드](https://nextjs.org/docs/app/guides/authentication)를 따른다.

## 6. 보정가 마스킹 계약

보정가는 내부 직원이지만 개인 식별 정보와 설문 전체가 필요하지 않다. 본인 retouch_jobs에 연결된 **선택 사진·보정 선호·사진별 수정 의견**만 투영한다. 이름·전화번호·전체 설문 answers·다른 촬영·다른 보정가 작업은 제외한다.

RLS는 행 범위를 제한한다. 열·중첩 JSON의 비공개는 마스킹 뷰·GRANT·허용 DTO로 함께 보장한다. 클라이언트에서 이름을 별표로 바꾸거나 요청 SELECT 목록에서만 빼는 방식은 충분한 인가가 아니다. 보정가에게 원본 customers·surveys를 직접 읽거나 다른 join을 통해 복원하는 경로를 열지 않는다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

보정 선호를 설문에서 추출할 때는 허용한 문항만 명시적으로 복사한다. 전체 answers를 내려준 후 화면에서 필요한 부분만 쓰는 구조를 피한다. 사진의 파일명·경로·댓글·추가 API 응답에도 고객 이름·연락처가 포함되는지 검증한다.

## 7. 서버·RLS·RPC 경계

### 원문 정책

- 고객 브라우저는 DB를 직접 조회하지 않는다. Next.js 서버가 고객 세션의 shoot_id를 확인한 뒤 서버 전용 elevated key로 해당 촬영 범위만 접근한다.
- 직원 브라우저 조회는 Supabase Auth와 RLS를 사용한다. active·role·현재 배정을 만족하는 행과 허용된 투영만 반환한다.
- 주요 변경의 원문 함수는 book_slot, confirm_payment, release_hold, cancel_shoot, share_plan, submit_selection, request_revision, resolve_request, change_status다.

### 설계 보완

중요 변경은 Next.js 서버에서 직원/고객 문맥을 검증한 후 DB 트랜잭션 함수로 통일한다. 함수가 상태·슬롯·결제·요청·타임라인·알림 예약을 한 번에 처리한다. 함수 실행 권한은 최소화하고 브라우저가 테이블을 직접 update해 업무 규칙을 우회하지 못하게 한다.

서비스키/secret key는 RLS를 우회하므로 서버에서 사용한다는 사실만으로 고객 간 분리가 보장되지 않는다. 고객 DAL은 검증된 session.shoot_id를 필수 인자로 사용하고, 함수 내부도 대상 촬영·현재 상태·허용 행위를 확인한다. 쿼리에서 shoot_id 필터를 빠뜨린 경우를 실제 거부 테스트로 검증한다. 브라우저 번들·공유 UI·공개 환경변수에 elevated key를 넣지 않는다. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)

목록·상세·검색·건수·파일 발급·타임라인·알림 응답에도 같은 범위를 적용한다. 화면 하나를 막았어도 건수·오류 메시지·미리보기로 다른 고객 정보를 노출하면 권한 검증 실패다. 직원 읽기용 client와 서버 elevated client는 별도 모듈로 분리한다.

## 8. 파일·사진의 접근 범위

| 자료                | 저장 위치                  | 권한                                         |
| ------------------- | -------------------------- | -------------------------------------------- |
| 설문·의상·후기 캡처 | private `customer-uploads` | 본인 고객 제출/공개 범위, 역할별 업무 범위   |
| 후보·보정·수정 사진 | private `photos`           | 촬영 소속·공개 상태·작업 배정별 확인         |
| 코디 참조 이미지    | private `plan-refs`        | 해당 코디안·촬영의 허용 범위                 |
| 촬영 원본           | 외부 드라이브 `file_links` | 촬영 소속·version·visible·역할을 확인한 링크 |

세 Supabase bucket을 모두 private으로 두고, 파일별 인가 후 짧은 서명 URL을 발급한다. 요청자가 보낸 bucket/path를 그대로 서명하지 않는다. 서버가 DB의 촬영·파일 관계와 공개 상태에서 허용된 객체 경로를 결정한다. Private bucket과 서명 URL의 접근 방식은 [Supabase Storage 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals)를 따른다.

설계 보완으로 업로드의 파일 종류·개수·크기·실제 형식·촬영 경로를 검증하고, 썸네일·미리보기·수정 버전에도 같은 권한을 적용한다. 공통 디자인 시스템 assets에는 고객 사진을 넣지 않는다.

서명 URL은 유효 기간 안에 전달될 수 있다. 직원 퇴사·재배정·공개 취소 후 새 URL 발급은 즉시 거부하되 이미 발급된 URL의 남은 유효 시간과 외부 드라이브 공유 권한은 따로 관리해야 한다. URL·토큰·고객 파일을 일반 로그나 공개 CDN 캐시에 남기지 않는다.

## 9. 동의·보존·삭제

서비스 수행에 필요한 개인정보·사진 처리 동의와 선택적인 사진 마케팅 활용 동의를 분리한다. 선택 마케팅 동의를 거절했다는 이유로 정상 서비스를 차단하지 않는다. 고객에게 원본·결과물을 공개하는 것과 회사가 광고 채널에 사진을 게시하는 것은 서로 다른 권한이다.

보정가는 내부 직원이므로 외주 제3자 제공 동의를 전제하지 않는다. 그래도 업무에 필요한 최소 정보와 배정 범위만 접근하게 한다. 실제로 외부 수탁자나 다른 업체에 고객 자료를 보내는 변경은 별도 정책 검토 대상이며 이번 설계에 미리 포함하지 않는다.

원문은 고객 업로드를 삭제 요청이 있으면 처리하고 그 외에는 보관하는 방향이다. **정확한 보존 기간·처리 기한·예외·삭제 범위는 미정**이다. 임의의 법정 기간이나 자동 보관 기간을 문서에 확정하지 않는다. 동의문 버전·동의/철회 시각·목적별 기록 방식은 설계 보완으로 정의해야 한다.

삭제 요청은 본인 확인 후 대상 촬영·uploads·Storage 객체·파생 파일·원본 외부 링크·캐시·백업·알림 기록에 미치는 범위를 정하고 처리 이력을 남긴다. 고객이 요청했다는 이유로 서비스 기록 전체를 즉시 물리 삭제하는 API로 해석하지 않는다. 요청 처리 권한과 보존 예외는 운영 정책으로 확정한다.

## 10. 감사와 출처 충돌

원문 timeline에 상태의 from/to·actor·reason을 기록한다. admin/staff의 스킵·역행·취소·배정 덮어쓰기는 사유와 변경 전후 담당/상태를 남긴다. 정상 고객 행위·시스템 전이도 누가 어떤 경로로 실행했는지 구분해야 한다.

설계 보완으로 권한 변경·active 변경·토큰 재발급·파일 공개·삭제 요청 처리에 대상·행위자·시각·결과·요청 식별자를 기록한다. 감사 기록에 세션·토큰·서명 URL·설문 전문·사진 본문을 저장하지 않는다. timeline 수정/삭제 권한을 일반 직원 CRUD로 노출하지 않는다.

**취소 시 담당자 보존은 출처 충돌로 미결이다.** Notion ERD v0.4는 cancel_shoot에서 director_id를 기록용으로 유지한다고 적었고, Canonical v1.11 12절은 취소 시 디렉터 해제라고 적었다. 제안은 현재 슬롯·배정을 해제하고 이전 담당자 이력은 timeline에 보존하는 것이다. 운영 결정 전 어느 한쪽을 확정 정책으로 구현하지 않는다. hold 해제 때 director_id를 비우는 것은 양쪽 자료가 일치한다.

## 12. 구현 전 남은 결정

IP 한도·세션 만료와 재방문 상세 동작, 전화번호 변경·토큰 재발급 운영 절차, 마지막 admin 보호·재인증, 역할별 모든 API/열 허용 목록, 파일별 URL 만료·보존·삭제 범위, 취소 시 담당자 이력 보존 방식을 확정한다. 각 결정은 원문 정책과 구분해 기록하고 권한 거부 테스트와 함께 검토한다.
